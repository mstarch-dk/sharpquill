00

What it is, and who it is for

Sharpquill is two web applications on one API: a public website, rendered on the server so pages arrive complete and are easy for search engines to read, and an admin panel where writers and editors create, organise and publish content. Articles are stored as Markdown in PostgreSQL; images live on disk next to the API.

It is deliberately small. One site per installation, a handful of containers, no plugin marketplace and no monthly bill beyond the server it runs on.

If you write

You get an editor that feels like a word processor but saves clean Markdown, a layout mode for richer pages, series for multi-part stories, previews and a version history, and a reader side with comments, likes and members-only posts. You change the site's name, theme and fonts in a settings page.

If you run the server

You get four published container images, a reference Compose file and Caddy config, separate hostnames for the public site and the admin, short-lived tokens with rotating refresh tokens, optional client-certificate login for the admin, backup and restore scripts, and plain SQL you can read. Section 09 covers it.

About the screenshots: they come from a demo installation filled with a fictional Danish gardening blog, Nyttehaven, with the site language set to Danish, so the public site's own texts (buttons, headings such as Seneste artikler, “latest articles”) are Danish too. Set the language to English and they switch. The admin panel is in English.

01

Writing and publishing

Articles and pages are written in the same editor. By default it is a rich-text editor with a toolbar (headings, bold, italic, lists, quotes, code, links, images); what it saves is Markdown, so content stays portable and readable outside the CMS. Switch on Simple Editor to edit the Markdown directly.

Around the text sit the things a published post needs: a slug, an excerpt for cards and search results, a meta title and description, a featured image with a display size (extra small, small, medium or original) and a header style (plain, image with the title overlaid, blurred image, or a gradient header), a category and tags, a publish date, the author name shown to readers, and switches for comments and for members-only access.

Scheduling needs no extra step: publish an article with a date in the future and the public site treats it as a draft until that moment, then shows it in lists, feeds and search on its own.

02

Block layouts for richer pages

Plain text is enough for most posts. When a page needs more structure, turn on layout mode and build it from sections (full width, two columns or three columns) that hold blocks:

  • Text in the same editor as above, and images with alt text and caption.
  • Steps (numbered cards), cards (an icon picked from 56 outline icons or an emoji, a title and a description) and a call to action with a button.
  • Link previews (title, description and image fetched from the URL), embedded posts from X, and code with syntax highlighting.
  • Containers that hold their own sections, nested up to three levels, and the contact form as a ready-made component.
03

Categories, tags, pages and menus

Each article has one category and any number of tags, and each category and tag gets its own page on the public site. Pages (About, Contact) are written in the same editor but stand outside the blog and its listings. Menus for the header and footer are edited in the admin: an item points to a page, to a built-in route (front page, blog, categories, series) or to an external address.

In the admin, the article list is searched by title and text, filtered by status (including scheduled), category and author, and sorted; the filters stay in the address, so a filtered list can be bookmarked.

04

Series

A series ties articles into an ordered sequence: a tutorial in parts, a season of posts, a story told over several weeks. You add articles to a series and put them in order in the admin. On the public site every article in a series shows where it sits (Del 4 af 4, “part 4 of 4”) with links to the previous and next part, and the series has its own page. A series can also use a theme of its own instead of the site's.

05

The public website

The public site is a Nuxt application rendered on the server: each page is sent as finished HTML with its title, description and social-sharing tags, and then becomes interactive in the browser. It has a front page with the latest articles, the blog with pagination, category, tag and series pages, the pages you write, sign-up and log-in, and a switch between light and dark mode. It works on a phone without a separate mobile site.

Readers find content through a search box in the header. While they type it suggests matching articles, tags, categories and series; Enter opens a results page ranked by PostgreSQL full-text search, with the matching words highlighted in a snippet. Quotes search for an exact phrase and a minus sign leaves a word out. No separate search service is needed, and members-only articles show up only for readers who are logged in.

Feeds in RSS 2.0 and Atom 1.0 cover the whole site and each category, tag and series (the 20 newest articles). Every page links the site's feeds, and category, tag and series pages also link their own, so feed readers find them from the page address.

Optional analytics come from a self-hosted Umami instance, which counts visits without cookies; leave its website id empty and no tracking script is loaded.

06

Readers: comments, likes and members

Comments can be switched on per article. Readers write a name, an email address (not shown) and the comment; replies are threaded one level. New comments wait in a moderation queue until someone approves them. A hidden honeypot field and a per-address rate limit keep most automated spam out. Likes need no account.

Reader accounts are optional. A reader signs up with name and email; an admin approves the account; the reader then logs in with a link sent by email, so there is no reader password to leak. Approved readers can open articles marked members only; everyone else sees a log-in prompt instead of the text. The whole log-in feature can be turned off in settings.

A contact form sends messages over SMTP to the address in settings. Until both are configured it answers that it is unavailable instead of losing messages.

07

Look and feel, from a settings page

The site's identity is data, not code: its name and description, the footer text ({year} is filled in), a public email, phone and company details for the footer, the site language, social links and meta keywords. The language sets the page's <html lang> and the public site's own texts and dates: Danish and English ship, and another language is one translation file. The appearance is chosen from eight colour themes and four fonts (Inter, Manrope, Source Serif 4, Atkinson Hyperlegible), and you decide whether the public site and the admin start in dark mode. Readers can switch between light and dark themselves.

08

Images

Images are uploaded from the editor or the Media page and kept in a shared library you pick from for featured images and image blocks. Uploads are checked by their content, not their file name: JPEG, PNG, GIF and WebP up to 10 MB and 40 megapixels are accepted. For each image the API stores a 400 px and an 800 px wide copy, and the site serves the smaller copies on cards and lists.

Deleting a file removes the original and both copies. While it is still used, as a featured image, in an article's text or layout, in a setting or as an avatar, the Media page lists where and asks before it deletes, so an image does not silently disappear from a published page.

08b

Export and import

The Packages page exports content as a ZIP file: everything, only articles, only pages or hand-picked items, optionally with tags, categories and site settings. Importing checks the package first and then adds it to the site. Use it to move a site to a new server, to copy content between a test and a live installation, or as a readable backup of the writing itself (the database backup in section 09 is the full one).

09

Running it yourself

A production site is one Linux server with Docker Compose. 2 vCPU and 2 GB RAM is enough to start. The project publishes four images (API, web, admin and a one-shot database initialiser) to the GitHub container registry; they are configured entirely through environment variables at start-up, so the same images serve every site. Caddy in front handles HTTPS certificates, routing and security headers.

Separate hostnames

The admin panel and its API run on their own hostname; the public host never routes admin API calls.

Short-lived tokens

JWT access tokens (15 minutes by default) with rotating refresh tokens in an HttpOnly cookie, and separate token audiences for authors and readers.

Client certificates

Optional mutual-TLS log-in for the admin, so the admin panel only opens on devices with your certificate.

Defensive defaults

Server-side HTML sanitising, URL-scheme checks in layouts, rate limits on log-in, comments and contact, a 12-character minimum for author passwords, and the API refuses to start with a weak JWT secret.

Readable data access

Hand-written, parameterised SQL through Npgsql at runtime; EF Core only for schema migrations, applied by db-init before the API starts.

Backups and upgrades

Backup and restore scripts for the database and uploads, a restore drill to prove backups work, and upgrades by changing one image version.

Built with AI agents. Most of the code was written by AI coding agents working from a task backlog, with a person deciding what to build and checking the results. The repository documents how that worked, including the security bugs the agents introduced and how they were caught (docs/ai-workflow.md). That is useful reading if you are deciding how far to trust the code, and it is why the project leans on integration tests against a real PostgreSQL.

10

Strengths and limits

What the CMS does well, and where it stops, so you can decide before you install it.

Strength: you own everythingContent, readers and analytics stay in your database on your server. Export packages and SQL backups keep it portable. MIT licence.
Strength: small and fastServer-rendered pages, a few containers, one small VM. No PHP stack, no plugin updates to chase.
Strength: a complete reader sideComments with moderation, likes, approved reader accounts with email log-in links, members-only articles and a contact form, without third-party services.
Strength: readers find contentSite search with suggestions as you type, and RSS and Atom feeds for the site and every category, tag and series, from the same PostgreSQL database.
Deliberately not included: plugins and multi-tenancyThere is no plugin system and no shared multi-site hosting, so there are no plugin updates to chase and no tenant boundaries to get wrong. Block types and embeddable components are built in, from one registry shared by the editor and the site; new ones are added in code. The only embeddable component today is the contact form.
Limit: two interface languagesThe public site's own texts ship in Danish and English; another language is a translation file and an image rebuild. One installation shows one language, not several side by side. The admin panel is English only.
Limit: one site per installationSeveral sites mean several Compose stacks. There are no per-site roles beyond admin and user.
Limit: you are the operatorUpdates, backups, SMTP for email and a server to run it on are yours to arrange. The deployment guide walks through them, but nobody does it for you.
11

Get started

Try it locally with Docker and Compose, from a clone of the repository:

cp .env.example .env
docker compose up -d
# public site: http://localhost:3000
# admin panel: http://localhost:3001
# first log-in: ADMIN_EMAIL / ADMIN_PASSWORD from .env,
#   or the generated password in: docker compose logs db-init

Run a site from the published images with the step-by-step guide in docs/deployment.md: DNS, configuration, Caddy, first log-in, backups and the restore drill. If your site collects reader data, read docs/privacy.md as well.
